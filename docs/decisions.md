## Decision Details

### Python engine + TS MCP wrapper
The PDF editing engine lives in this repo (Python). A separate TypeScript repo will wrap it
as an MCP server. fonttools has no viable JS/TS equivalent, making Python mandatory for the
core engine. The MCP SDK is TypeScript-native, so the wrapper lives separately.

### E.7 cross-line "\n" grouping-boundary join: space-delimited-aware (v0.2.0, 2026-06-01)
The E.7 within-segment recorded-separator model (`linebreak.recorded_separators`,
byte-faithful) is correct, but the CROSS-LINE element-grouping `"\n"` join
(`reflow._rejoin_newline_artifacts` → `linebreak.grouping_boundary_separator`) still
used CHARACTER-CLASS INFERENCE (`if right_cls == "ID" and left_cls in ("ID","CL"):
return ""`). Korean Hangul is East-Asian-width W, so `_char_class` returns `"ID"` on both
sides of a source-line `"\n"` boundary; the ID|ID rule returned `""` and GLUED the last
word of one source line to the first of the next, silently deleting the Korean word space
(`"프로젝트 관리자" / "김철수…"` reflowing to `"…관리자김철수…"`, success=True). Pre-E.7 did a
blanket `"\n"->" "` here, which PRESERVED that space — so this was an E.7-introduced
regression.

A `"\n"` artifact is a LOCATOR-inserted element-grouping boundary with NO per-boundary
original-space provenance (the "was there a space here" info was discarded at extraction;
recovering it perfectly is a READ-PATH change carved out to 0.3.0), so the cross-line join
must use the best reflow-side heuristic. ROOT FIX (space-delimited-aware; strictly NO
space-fidelity regression vs pre-E.7): the `"\n"` separator is `" "` when the paragraph is
SPACE-DELIMITED — its combined source text contains any ASCII space/tab (Latin / mixed /
CJK-with-spaces) OR any Hangul (Korean is a space-delimited script whose syllables are
otherwise indistinguishable from Han ideographs at the char-class level, so a short Korean
fragment like `"관리자"` carries no literal space yet a `"\n"` beside it is a word boundary)
— and `""` only for a PURE no-space Han/Kana ideograph paragraph. So Korean / Latin / mixed
re-join with `" "` (word spaces PRESERVED, matches pre-E.7), and pure no-space CJK re-joins
with `""` (no spurious inter-line space, an IMPROVEMENT over pre-E.7's blanket space). The
paragraph-level decision lives in `reflow._rejoin_newline_artifacts` (new
`linebreak.is_space_delimited_script` predicate, stdlib-only); `grouping_boundary_separator`
gains an optional `space_delimited: bool = True` parameter (default `True` is the
pre-E.7-faithful, never-glue default, so the 2-arg call surface is unchanged). The
within-line recorded-separator model, the pure-Latin `is_latin_simple` fast path, and the
CJK wrapping / bracket rules are UNTOUCHED. INV-G-10 grows section (l) cross-line probes
(Korean preserved, pure-CJK empty control, Latin space control, separator-decision unit,
public `replace(reflow=True)` e2e); the e2e fixture column was widened (via a wide line2,
which sets the locator right-margin) so the re-wrapped paragraph breaks only at word
boundaries and the `"\n"->" "` flatten measures the cross-line join, not a mid-word Korean
syllable wrap.

RESIDUAL (heuristic, by design): a CJK-WITH-INTERNAL-SPACES paragraph (so `space_delimited`
is True) whose source line broke EXACTLY at an ideograph-ideograph boundary may get a
spurious `" "` at that `"\n"`. This is identical to pre-E.7 behaviour (which inserted a
space at every `"\n"`), so it is NOT a regression; the perfect per-boundary fix needs the
read-path provenance carved out to 0.3.0. Documented at the helper docstrings in
`linebreak.grouping_boundary_separator` and `reflow._rejoin_newline_artifacts`.

### parse_content_stream over TokenFilter
pikepdf's TokenFilter processes tokens in a streaming fashion but doesn't support random
access to specific operators. Our approach requires locating specific text operators by index
and modifying them in place. parse_content_stream returns a list of (operands, operator)
tuples that can be indexed, modified, and re-serialized via unparse_content_stream.

### Identity-H as primary encoding
Real-world testing (resumes, business documents) showed that modern PDFs overwhelmingly
use CIDFont with Identity-H encoding. WinAnsi and other encodings exist but are secondary.
The engine handles Identity-H first and falls back to simpler encodings.

### FidelityReport as differentiator
Competing approaches (PyMuPDF redact-and-replace) silently degrade formatting. Our engine
returns a FidelityReport with every edit, documenting exactly what changed: whether fonts
were preserved or substituted, whether overflow occurred, and which glyphs (if any) could
not be rendered. This is critical for AI agent consumers that need to verify edit quality.
